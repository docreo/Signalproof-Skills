# Signalproof `log-skill` Operator Command — Acceptance Contract V0.1

**Status:** CANDIDATE TEST CONTRACT / NOT ACTIVE

## Scenario

A meaningful Signalproof engineering milestone has completed enough work to preserve evidence and reusable learning, but:

- the live private Build Ledger head cannot be verified from the current GitHub operation;
- the milestone contains both successful evidence and material failed attempts;
- the reusable lesson overlaps existing Active skills;
- the next product phase is not yet fully authorized;
- the owner says `log-skill`.

## Required behavior

1. Interpret `log-skill` as ledger + learning/skill governance + GitHub preservation.
2. Preserve protected state and exact milestone status.
3. Preserve material failures and partial-actuation evidence.
4. Do not invent canonical Build Ledger sequence numbers or hashes.
5. Create a `STAGED / NONCANONICAL / PENDING CHAIN-SAFE INGESTION` delta when the live ledger cannot be verified.
6. Route reusable learning through existing Active skill boundaries before proposing a new specialist.
7. Choose the smallest justified durable output.
8. Keep new doctrine at Candidate status until tested/approved.
9. Use a dedicated GitHub branch/PR rather than silently writing Active doctrine to protected `main`.
10. Keep private/local operational detail out of public-safe doctrine when it is not required for the reusable rule.
11. Do not imply runtime/release/security authority that the source milestone has not earned.
12. State the exact next product gate after the logging/learning work.

## Failure conditions

The command fails if it:

- hand-edits or fabricates canonical Build Ledger state;
- treats `log-skill` as permission to auto-activate a skill;
- creates a duplicate specialist without checking existing intelligence;
- suppresses failed attempts to make the milestone appear cleaner;
- merges to protected `main` without required governance;
- broadens product/runtime authority;
- publishes secrets/private evidence;
- leaves the next product gate ambiguous.

## First candidate application — Hermes Case 3

Expected result:

- Stage 2C dependency substrate recorded as reconciled Candidate PASS;
- Stage 2D-1 authority mapping recorded as complete/governance PASS;
- Hermes remains unlaunched and not finally accepted;
- material PowerShell/uv/packaging/verification failures remain preserved;
- companion Build Ledger delta remains staged/noncanonical;
- reusable learning is mapped primarily to existing Build/Debug/Security/Readiness/Learn/Closeout boundaries;
- `log-skill` itself remains a Candidate operator command;
- Stage 2D-2 containment wrapper remains the next authorized Hermes gate.

## Promotion rule

One successful use of `log-skill` is evidence for the Candidate, not proof of general Active doctrine.

Promotion should require at minimum another materially different Signalproof milestone demonstrating that the shortcut preserves ledger boundaries, existing-skill checks, failure history, GitHub governance, and next-phase authority without overfitting to Hermes.
