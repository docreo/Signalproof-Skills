# `build-git this` — Active Operator Command V0.1

**Status:** ACTIVE  
**Version:** 0.1.0  
**Owner:** Doc Reo

## Purpose

`build-git this` turns the currently established subject, decision, or accepted design into the next governed Git-backed action.

It is narrower than generic `build-git`: `this` binds the command to the current clearly established work unit.

## Required behavior

1. Resolve the current work unit and acceptance boundary. If `this` is ambiguous, STOP and resolve scope before writing.
2. Refetch the relevant Git repository and current base/head before consequential action.
3. Route the minimum applicable Active Signalproof capability set.
4. Run Known Failure Preflight for consequential or materially failure-prone work.
5. Establish protected state, forbidden-change boundary, rollback/non-mutation boundary, and required evidence.
6. Execute only the next governed action required by current evidence. This may be Research, Investigate, Evaluate, Plan, Design, Readiness, Build, Debug, Verify, Review, Security, Recovery, Document, Release, Learn, Handoff, or Closeout.
7. Verify affected boundaries incrementally.
8. Use a branch/PR for protected repositories when repository rules require it.
9. Recheck Git state before consequential promotion/merge/publication.
10. Leave proof and preserve failures/uncertainty rather than reporting false completion.

## Relationship to `build-git`

`build-git this` is the operator shorthand for applying the governed `build-git` workmode to the current bounded subject. It does not make candidate `build-git` policy Active by itself and does not create authority beyond the routed Active Skills and owner approval already present.

## Completion

Complete when the current bounded work unit has reached its accepted Git-backed milestone, or STOP when evidence, authority, protected state, licensing/security, or an unresolved human decision prevents responsible continuation.

## STOP conditions

STOP when Git current state cannot be established, `this` is ambiguous, protected state would be weakened outside authority, the same known failure would be repeated without changed evidence, repository rules require a gate that cannot be satisfied, or canonical Build Ledger/release/production authority is being inferred rather than established.
