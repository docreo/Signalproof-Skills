# `build-git this` - Active Operator Command V0.1

**Status:** ACTIVE  
**Version:** 0.1.0  
**Owner:** Doc Reo

## Purpose

`build-git this` applies the governed `build-git` workmode to the current clearly established work unit.

`this` binds execution to the subject, decision, accepted design, or bounded milestone already established in the conversation/evidence. It is narrower than generic `build-git`.

## Required behavior

1. Resolve the current work unit and acceptance boundary. If `this` is ambiguous, STOP and resolve scope before writing.
2. Refetch the relevant repository and current base/head before consequential action.
3. Route the minimum applicable Active Signalproof capability set.
4. Run Known Failure Preflight for consequential or materially failure-prone work.
5. Establish protected state, forbidden-change boundary, rollback/non-mutation boundary, and required evidence.
6. Execute only the next governed action required by current evidence. This may be Research, Investigate, Evaluate, Plan, Design, Readiness, Build, Debug, Verify, Review, Security, Recovery, Document, Release, Learn, Handoff, or Closeout.
7. Verify affected boundaries incrementally.
8. Use a branch/PR for protected repositories when required.
9. Recheck Git before consequential promotion, merge, publication, or release.
10. Leave proof and preserve failures/uncertainty rather than reporting false completion.

## Relationship to `build-git`

`build-git this` is a binding form of Active `build-git`. It does not create authority beyond the underlying Active skills, current owner authorization, repository rules, and other applicable governance gates.

## Completion

Complete when the current bounded work unit reaches its accepted Git-backed milestone, or STOP when evidence, authority, protected state, licensing/security, repository rules, or an unresolved human decision prevents responsible continuation.

## STOP conditions

STOP when current Git cannot be established; `this` is ambiguous; protected state would be weakened outside authority; the same known failure would be repeated without changed evidence; repository-required gates cannot be satisfied; or canonical Build Ledger, release, privilege, credential, security-change, production, or Candidate-activation authority is being inferred rather than established.
