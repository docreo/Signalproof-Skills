# `/handoff-log` — Operator Command V0.2 Candidate

**Status:** CANDIDATE / NOT ACTIVE  
**Supersedes if promoted:** Active V0.1  
**Version:** 0.2.0-candidate  
**Date:** 2026-08-18  
**Owner direction:** Handoffs should be lean, Git-directed, provenance-preserving transfer packets that bootstrap the receiving chat automatically.

## Purpose

`/handoff-log` creates a governed transfer package for continuing Signalproof work in another chat/session without requiring the human to retell the conversation.

Its central rule is:

> **Transfer the mission, provenance, authority, protected state, and retrieval path — not the entire chat.**

The handoff must contain enough information for the receiving chat to locate the authoritative current records and continue safely, but it should avoid duplicating large bodies of repository-controlled doctrine that can be retrieved from GitHub.

## Required operation

`/handoff-log` performs two responsibilities:

1. preserve/synchronize the current meaningful work state under `/log-skill` semantics; and
2. produce a lean receiving-chat handoff whose first executable instruction is `/log-build-git`.

The handoff does **not** itself imply milestone closeout, canonical Build Ledger append, release, deployment, or candidate activation.

## Mandatory receiving-chat bootstrap

Every `WORK-CHAT-HANDOFF.md` generated by `/handoff-log` must begin with a visible receiving-chat instruction equivalent to:

```text
RECEIVING CHAT — START HERE

Run: /log-build-git

Treat this handoff as a provenance-bound transfer packet, not as complete current truth.
Before consequential work:
1. Refetch docreo/Signalproof-Skills main.
2. Read the current command definitions required for this mission, beginning with:
   - commands/log-build-git.md
   - commands/design-git.md
   - commands/build-git.md
   - commands/handoff-log.md
3. Read the current signalproof-router and only the Active specialist skills it routes for the next action.
4. If private repository access is available, refetch docreo/Signalproof-Build-Ledger main and retrieve only the task-relevant private continuity, handoff, evidence, failure intelligence, protected-state, and staged/canonical ledger records.
5. If private access is unavailable, continue from public Signalproof-Skills plus the evidence embedded/referenced in this handoff; explicitly mark private continuity as UNAVAILABLE rather than guessing it.
6. Record receipt of this handoff through /log-build-git before designing/executing the next action.
7. Revalidate the stated Next Gate against current Git/evidence before mutation.
```

The receiving chat must not interpret the command names or workflow from memory when current Git definitions are available.

## Handoff-first `/log-build-git` meaning

When `/log-build-git` is the first command executed from a `/handoff-log` transfer, the receiving chat should treat it as a **receipt + bootstrap + continuation** invocation:

1. acknowledge and preserve the transfer identity;
2. refetch current command and skill authority from GitHub;
3. resolve private/public continuity according to access;
4. deduplicate the receipt against existing handoff/log records;
5. preserve the prior build/work-stream identity and open/closed state;
6. run Known Failure Preflight for the intended next action;
7. produce a fresh Next Action Contract from current truth;
8. execute only the routed action authorized by that contract.

This receipt does not automatically close the transferred milestone.

## Git is the doctrine source, handoff is the mission index

Do not copy entire current command/skill bodies into `WORK-CHAT-HANDOFF.md` merely to make it self-contained.

Instead, the handoff should point the receiver to:

- `docreo/Signalproof-Skills/main` for current public command/skill doctrine;
- the current `signalproof-router` for Active routing authority;
- exact public candidate files only when the current mission materially depends on candidate behavior and the handoff explicitly identifies their lifecycle state;
- `docreo/Signalproof-Build-Ledger/main` for private continuity when accessible;
- exact project repositories, branches, PRs, commits, artifacts, manifests, hashes, or evidence files required for the current mission.

A Git SHA recorded in the handoff is a transfer snapshot. The receiving chat must still refetch volatile `main` before consequential writes.

## Private-first continuity with public fallback

For Signalproof work, `/handoff-log` should prefer the strongest available continuity evidence in this order:

1. verified current private Build Ledger / private project evidence, when access exists and is relevant;
2. current public Signalproof-Skills/project Git evidence;
3. evidence directly embedded in or attached to the handoff;
4. explicit UNKNOWN / UNAVAILABLE state.

Never substitute memory, inference, or a stale projected ledger state for unavailable private evidence.

When private access exists, retrieve only the smallest task-relevant private records. Do not preload the entire private repository.

When private access does not exist, the handoff must contain enough public-safe mission state to proceed to a read-only verification/investigation gate or STOP safely.

## `START-HERE-NEW-CHAT.txt`

The minimal companion file should be extremely short:

```text
This is a Signalproof governed handoff.
Read WORK-CHAT-HANDOFF.md first.
Then run /log-build-git.
Use current GitHub definitions, not memory.
Prefer private Build Ledger continuity when accessible; otherwise use public Git and mark private state unavailable.
Do not mutate consequential state until the transferred Next Gate is revalidated.
```

## Provenance receipt

The receiving `/log-build-git` invocation should preserve, where available:

- handoff ID;
- source chat/work-stream identity;
- handoff artifact hash;
- source Git snapshots stated in the handoff;
- receiving-time current Git snapshots;
- whether private continuity was accessible;
- records actually retrieved;
- material differences discovered since handoff creation;
- fresh Next Action Contract;
- resulting evidence/status.

This creates a durable provenance chain:

```text
SOURCE CHAT
   ↓ /handoff-log
HANDOFF ARTIFACT + HASH
   ↓
RECEIVING CHAT
   ↓ /log-build-git receipt
CURRENT GIT / PRIVATE-PUBLIC RECONCILIATION
   ↓
NEXT ACTION CONTRACT
   ↓
GOVERNED CONTINUATION
```

## `/log-skill` behavior at handoff creation

Before finalizing the handoff:

- preserve meaningful milestone/learning state;
- preserve failures and uncertainty;
- preserve pending `close-when-complete` obligations;
- deduplicate existing records;
- separate public-safe from private evidence;
- preserve build/work-stream identity;
- do not reserve a canonical C-number;
- do not treat a projected sequence as live chronology;
- do not auto-activate candidate outputs.

If the underlying milestone is actually complete and closure is explicitly requested/required, use the appropriate `/log-skill close` form separately. Otherwise the handoff preserves OPEN state.

## Command/skill lifecycle rule

The receiving chat must distinguish current Git presence from lifecycle authority.

- Active commands/skills may govern work according to their contracts.
- Candidate command/skill files may be read for the mission when explicitly relevant, but their presence in `main` does not automatically make them Active.
- A handoff must not activate a candidate by instruction alone.
- If the handoff depends on Candidate behavior, state that explicitly and preserve any required owner/acceptance gate.

## Idempotency

Repeated `/handoff-log` on the same transfer should refresh/supersede the existing transfer identity rather than create duplicate parallel handoffs.

Repeated receiving `/log-build-git` should detect an already-recorded handoff receipt and continue from current evidence rather than recording the same exchange twice.

## STOP conditions

STOP when:

- the handoff cannot identify the work stream or exact next gate;
- protected state or authority is materially ambiguous;
- public/private boundaries cannot be preserved;
- Git doctrine/current project evidence cannot be refetched and the next action would require guessing;
- private continuity is required for safe mutation but unavailable;
- chronology would be fabricated;
- a candidate would be silently treated as Active;
- the receiver would have to reconstruct critical state from conversational memory instead of available artifacts/Git;
- the handoff is so verbose that it duplicates repository-controlled doctrine instead of indexing it.
